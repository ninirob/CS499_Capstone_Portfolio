Artifact Description

The Quantigration RMA (Return Merchandise Authorization) database was originally created during DAD 220: Introduction to Structured Database Environments. It models a fictional networking equipment company's return process across three related tables: Customers, Orders, and RMA. The original artifact included a full schema with primary and foreign key constraints, a Collaborators view, and a set of raw SQL CRUD operations. All original work was completed inside a Codio cloud environment using MySQL.

What Was Improved

Two core weaknesses drove this enhancement. The original data import relied on LOAD DATA INFILE statements hardcoded to Codio's file system, making the artifact entirely non-portable. All CRUD operations were also written as raw SQL strings with no credential management or SQL injection protection.

  • Created a least-privilege MySQL user (collaborator_viewer) with SELECT access scoped exclusively to the Collaborators view, with no access to base tables and no write privileges anywhere in the database.
  • Moved all database credentials into a .env file managed by python-dotenv, excluded from version control via .gitignore so no real credentials appear in any published file.
  • Replaced LOAD DATA INFILE with a portable Python data loader using mysql-connector-python and parameterized executemany calls.
  • Rewrote all CRUD operations as parameterized Python functions, separating query structure from data values at every point to eliminate SQL injection risk.
  • Wrapped multi-step write operations in explicit transactions so that a failure in either step rolls back the entire operation rather than leaving the database in an inconsistent state.

Course Outcomes

This enhancement was planned specifically to address outcome five and advances outcomes three and four as well.

CS-499-03

Reflected in the deliberate choice to prioritize security and portability over the simplicity of the original raw SQL approach, with trade-offs documented explicitly in the code.

CS-499-04

Demonstrated through the use of industry-standard tools including mysql-connector-python, python-dotenv, virtual environments, and transaction management.

CS-499-05

Met through a three-layer security approach: least-privilege access control at the database user level, environment-based credential management, and parameterized queries eliminating SQL injection risk across all CRUD operations.

Reflection

One of the more unexpected parts of this enhancement was discovering how much IntelliJ IDEA Ultimate simplified the verification process. The built-in Database tool window provided a live visual grid of table contents after each operation, making it easy to confirm that data was landing correctly without switching contexts.

One moment that reframed how I was thinking about this work was hitting MySQL's secure-file-priv restriction when running the original LOAD DATA INFILE statements locally. The error was not just an inconvenient obstacle — it was a live demonstration of exactly the problem the enhancement was designed to solve. MySQL's own security layer was blocking the original approach for the same reasons I was replacing it.

The main challenge was a password mismatch between the .env file and my actual MySQL root password, which surfaced an important distinction: IntelliJ's database connection and the Python script's connection are entirely independent. A working visual connection in the IDE does not guarantee that application-level credentials are correct. Diagnosing this reinforced that credential management deserves deliberate verification during setup, not just during a security review after the fact.
